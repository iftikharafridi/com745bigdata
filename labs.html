The university dataset (university_db)

Built from the Practical 0 scenario: lecturers, courses, modules and students, plus the registrations that link students to modules. All names, emails and dates are invented.

Files: university_schema.sql (tables and constraints) and university_seed.sql (rows). Run them in that order in MySQL Workbench or with mysql -u root -p < university_schema.sql. Running the schema script again drops and rebuilds the database, which is how you reset it.

Deliberate teaching cases
  • John Smith (1003) has no registrations: shows LEFT JOIN and NULL.
  • COM750 Artificial Intelligence has no students: insertion anomaly, COUNT(*) vs COUNT(column).
  • Dr Thomas Harris (6) delivers no module: partial participation.
  • Ryan O'Neill (1023): an apostrophe to escape ('O''Neill').
  • Emma Brown (1018) shares a surname with Dr Brown: why names are not keys.
  • Half the students have no Mobile: practise IS NULL.
Rules the database enforces
  • Lecturer rank 1-40; course level 4-8; student enrolment level 1-20; credits > 0 (CHECK).
  • Every course has a coordinator and every module a lecturer (NOT NULL foreign keys).
  • Emails are unique for students and for lecturers.
  • A student registers on a module at most once (composite primary key).
  • New students are 'Active' unless stated (DEFAULT).

The same university as documents (MongoDB)

File: university_mongo.js. In mongosh, from the folder holding it: load('university_mongo.js'). It drops and rebuilds uni_db and prints the counts: 6 lecturers, 3 courses, 6 modules, 24 students.

One reasonable document design (Practical 3 asks you to devise your own): students embed their registrations; modules and courses reference lecturers by _id; courses list their module codes. Values that are NULL in MySQL are left out of the documents.

CollectionShapeFrom MySQL
lecturers{ _id: 1, name: { forename, middle?, surname }, dateOfBirth, email, rank }Lecturer
courses{ _id: 'MSCCST', name, level, coordinatorId, modules: ['COM745', …] }Course + CourseModule
modules{ _id: 'COM745', name, credits, lecturerId }Module
students{ _id: 1001, forename, middleName?, surname, dateOfBirth, email, mobile?, level, course, status, registrations: [ { module, date, semester } ] }Student + Registration

The documents are generated from the MySQL tables by a script, so both versions always hold the same people, modules and registrations.

The same university as a graph (Neo4j)

File: university_graph.cypher. Paste it into Neo4j Browser (multi-statement editor on) or run cypher-shell -f university_graph.cypher. It deletes everything in the database, then creates 39 nodes and 71 relationships, and lists the node counts. Also: friends_books.cypher, the two-friends-and-a-book example from Lecture 6.

Smart-campus sensor data (InfluxDB)

File: campus_sensors.txt (synthetic). Load it from a terminal, in the folder holding the file: influx -import -path=campus_sensors.txt -precision=s. It creates the database campus and reports 95 inserts, 0 failed.

Three campus rooms on one teaching day, Monday 2 February 2026, 08:00-18:00 UTC (UK time in February is UTC). Occupancy follows a timetable; CO2 and temperature rise when a room is in use. One lab_2 reading, at 12:30, is missing on purpose so that fill() has something to fill.

MeasurementTagsFieldsPoints
room_envroom (lab_1, lab_2, lecture_a), room_type (lab, lecture)temp_c (float), humidity (float), co2_ppm (integer), occupancy (integer)62: every 30 minutes, 21 per room (lab_2: 20)
energyroomkwh (float)33: hourly, 11 per room

Rooms: lab_1 (capacity 30), lab_2 (24), lecture_a (80). The file is in influx -import format: a # DDL section with CREATE DATABASE, then a # DML section of line-protocol points with second timestamps.
