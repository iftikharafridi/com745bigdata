A

Understand

From tables to documents: what changes, and why.

A1

Why documents?

Look back at Practical 1. Six tables for one university, two of them only there to hold many-to-many links, and a three-table JOIN to answer "which modules is Ahmed on?". A document database stores each record as a self-describing document that can hold nested objects and lists, so data that is read together can be stored together.

Documents are written in a structured text format. Three you will meet:

FormatLooks likeStrengths and weaknesses
JSON{ "forename": "Ahmed", "modules": ["COM745", "COM746"] }Today's standard for data exchange; human-readable; platform-neutral. No date type.
XML<student><forename>Ahmed</forename>…Human-readable but verbose; costly to parse and store. Mostly legacy systems.
BSONBinary JSON (not human-readable)What MongoDB stores and sends. Faster to scan, and adds types JSON lacks: Date, ObjectId, Int32/Int64, Decimal128.
JSON typeExampleUse it for
string'COM745'Text, codes, phone numbers
number20Quantities you calculate with
booleantrueYes/no facts
nullnullKnown to be empty (often you simply leave the field out)
object{ forename: 'Laura', surname: 'Wilson' }A group of fields: a composite attribute, or an embedded record
array['COM745', 'COM746']Lists: the multivalued attributes that needed extra tables in Week 1
A2

Documents, collections and databases

Relational (MySQL)Document (MongoDB)Note
Database / schemaDatabaseuse uni_db creates it when you first write to it
TableCollectionNo column definitions: documents in one collection may differ
RowDocumentCan nest objects and arrays
ColumnFieldA missing field is simply absent, not NULL
Primary key_idEvery document has one, unique and indexed; MongoDB adds an ObjectId if you don't
JOINEmbedding, or $lookupEmbed what is read together; $lookup the rest

An ObjectId is a 12-byte value: a timestamp, a random part and a counter. It is unique without asking a central server, which matters when many servers insert at once. When your data already has a natural key (a student number, a module code), using it as _id keeps queries readable, as uni_db does.

A3

Modelling: embed or reference?

Normalisation in Week 1 asked "is each fact stored once?". Document modelling asks a second question first: which data is read together?

  • Embed a child inside its parent when it belongs to that one parent, is read with it, and stays small (a document is limited to 16 MB).
  • Reference it by _id when it is shared by many parents, changes on its own, or can grow without limit.
A4

Querying with find()

db.collection.find(filter, projection). The filter is a document of conditions: several conditions mean AND. The projection picks fields (1 to show, 0 to hide; _id shows unless you say _id: 0). Chain .sort(), .limit() and .skip() after it; use countDocuments(filter) to count.

SQLMongoDB filter
WHERE status = 'D'{ status: 'D' }
WHERE qty > 10 AND qty < 30{ qty: { $gt: 10, $lt: 30 } }
WHERE a = 1 OR b < 5{ $or: [ { a: 1 }, { b: { $lt: 5 } } ] }
WHERE status IN ('A','D'){ status: { $in: ['A', 'D'] } }
WHERE Mobile IS NULL{ mobile: { $exists: false } } (or { mobile: null }: missing or null)
WHERE Surname LIKE 'B%'{ surname: /^B/ }
nested column{ 'size.uom': 'in' } (dot notation, in quotes)
JOIN … WHERE r.ModuleCode = 'COM745'{ 'registrations.module': 'COM745' } (matches any array element)

Update operatorDoesExample

The replacement trap (Lecture 4). db.students.update({ surname: 'Parker' }, { surname: "O'Parker" }) replaces the matching document with { surname: "O'Parker" }: every other field is lost. updateOne refuses an update without operators, which is one reason it replaced update(). Results report matchedCount (found) and modifiedCount (actually changed): they differ when the value was already the same.

A6

The aggregation pipeline

db.collection.aggregate([stage, stage, …]) passes documents through stages in order, each stage feeding the next. It is MongoDB's GROUP BY, HAVING, ORDER BY and JOIN in one tool.

StageDoesSQL
$matchKeeps documents matching a filterWHERE (before $group) · HAVING (after)
$groupOne output per key, with accumulators ($sum, $avg, $min, $max, $push)GROUP BY
$unwindOne document per element of an arraynone: turns embedded data back into rows
$lookupAdds matching documents from another collection, as an arrayLEFT JOIN
$projectChooses and computes fieldsSELECT list
$sort · $limit · $countOrder · cap · countORDER BY · LIMIT · COUNT(*)
A7

Indexes, and when to choose MongoDB

Every collection has an index on _id. db.students.createIndex({ surname: 1 }) adds another; { unique: true } makes it enforce an alternate key, like UNIQUE in MySQL. explain() shows COLLSCAN (every document read) or IXSCAN (index used), MongoDB's version of MySQL's type ALL and ref.

Good fit
  • Records naturally shaped as documents (a student with their registrations, a product with its options)
  • Fields that vary between records
  • Reading a whole record at once
  • Scaling out across servers (sharding) for very large or fast data
Think twice
  • Many-to-many data queried from every direction
  • Transactions across many documents on every request (supported since 4.0, but costly)
  • A strict schema you want the database to enforce everywhere
  • Heavy ad hoc reporting across collections

This is an LO2 judgement, and CW2 asks you to make it about your own data: justify the choice from the data and the questions, not from fashion.

Pattern
SELECT Surname FROM Student WHERE Surname LIKE 'B%' ORDER BY Surname;

DISTINCT
SELECT DISTINCT Semester FROM Registration ORDER BY Semester;
db.students.distinct('registrations.semester')
GROUP BY
SELECT CourseCode, COUNT(*) FROM Student
GROUP BY CourseCode ORDER BY CourseCode;
db.students.aggregate([
  { $group: { _id: '$course', n: { $sum: 1 } } },
  { $sort: { _id: 1 } }
])
JOIN through a link table
SELECT s.StudentID FROM Student s
JOIN Registration r ON r.StudentID = s.StudentID
WHERE r.ModuleCode = 'COM748'
ORDER BY s.StudentID;
db.students.find({ 'registrations.module': 'COM748' }, { _id: 1 }).sort({ _id: 1 })
JOIN to a referenced table
SELECT m.ModuleCode, l.Surname FROM Module m
JOIN Lecturer l ON l.LecturerID = m.LecturerID
ORDER BY m.ModuleCode;
db.modules.aggregate([
  { $lookup: { from: 'lecturers', localField: 'lecturerId', foreignField: '_id', as: 'l' } },
  { $project: { surname: { $first: '$l.name.surname' } } },
  { $sort: { _id: 1 } }
])
GROUP BY over a link table + HAVING
SELECT ModuleCode, COUNT(*) AS n FROM Registration
GROUP BY ModuleCode HAVING COUNT(*) >= 6
ORDER BY ModuleCode;
db.students.aggregate([
  { $unwind: '$registrations' },
  { $group: { _id: '$registrations.module', n: { $sum: 1 } } },
  { $match: { n: { $gte: 6 } } },
  { $sort: { _id: 1 } }
])

Checked: each pair returns the same values from MySQL 8.0.46 and from the MongoDB emulator (9 of 9).

Practical 3: Data modelling in document databases

Scenario (as Practical 0)

A university wishes to store information about students, modules, courses and lecturers. Courses have a unique course code, course name and an accreditation level (4-8). Each course has a coordinator, which is a lecturer. Courses consist of modules. Modules have a name, unique module code and are delivered by a nominated lecturer. Lecturers have unique employee numbers, forenames, middle names and surnames, a date of birth, an email address and a rank of seniority (1-40). Students have unique student numbers, forenames, middle names and surnames, a date of birth, an email address and a current enrolment level (1-20).

  1. T0For some reason, the University has decided to store all its records as JSON. List the attribute types in the scenario and read about JSON to decide how to represent each type. Pay attention to arrays and sub-objects. JSON at json.org
    Hint

    JSON has string, number, boolean, null, object and array. BSON (what MongoDB stores) adds Date, ObjectId, Int32/Int64, Decimal128. A date of birth is best stored as a Date, not text.

    Hint

    For each relationship ask: is the child read together with the parent, owned by one parent, and bounded in size? Then embed. Shared or unbounded? Reference by _id. Try the embed-or-reference explorer in Part A.

  3. T2Explain the rationale for the strategy you produced.
    Hint

    Name the queries your design makes easy (one read) and the ones it makes harder ($lookup). Say where you accepted duplication and why.

  4. T3Find MongoDB on your workstation and start it, ready for Practical 4. On your own machine, install MongoDB Community Server, mongosh and MongoDB Compass. Install MongoDB Community Edition

Enforce a structure when you want one

A JSON Schema validator makes MongoDB refuse documents without the fields you require:

db.createCollection('lecturers2', {
  validator: { $jsonSchema: {
    bsonType: 'object',
    required: ['email', 'rank'],
    properties: {
      rank: { bsonType: 'int', minimum: 1, maximum: 40 }
    }
  } }
})

F3

Common misconceptions

Students often say…Correct it to…
"MongoDB has no schema, so design doesn't matter."The database doesn't enforce one, so the design lives in your code and your choices. A poor document design costs as much as a poor table design.
"Embed everything: that's the point of documents."Embed what is owned, read together and bounded; reference what is shared or grows.
"update() changes the fields I give it."Only with operators. Without $set the legacy update() replaces the whole document.
"MongoDB can't join."$lookup joins at query time. It is just not the first tool you reach for.
"A missing field and a null field are the same."{ f: { $exists: false } } finds only missing; { f: null } finds missing or null.
"use uni_db created the database."It only selects it. The database exists once something is written to it.
"NoSQL means no transactions."MongoDB has single-document atomicity always and multi-document transactions since 4.0, with a performance cost.

F5

Key terms

Aggregation pipeline
A list of stages ($match, $group, …) that documents pass through in order.
BSON
Binary JSON: how MongoDB stores documents; adds types such as Date and ObjectId.
Collection
A group of documents, the equivalent of a table, with no fixed columns.
Document
A record made of field-value pairs, which may nest objects and arrays.
Embedding
Storing related data inside a document (a student's registrations).
Filter
The document of conditions passed to find(), updateOne() etc.
mongosh
The MongoDB shell. Replaced the legacy mongo shell.
ObjectId
A 12-byte unique id (timestamp, random value, counter) MongoDB generates for _id.
Projection
The second argument of find(): which fields to return.
Referencing
Storing another document's _id instead of a copy; joined with $lookup.
Upsert
Update the matching document, or insert one if none matches.
Write concern
How many nodes must confirm a write before it is acknowledged (w:1, majority).
