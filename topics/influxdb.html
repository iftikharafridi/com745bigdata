A

Understand

Why time gets a database of its own, and how InfluxDB stores it.

A1

What is time-series data?

A time series is a sequence of measurements, each stamped with the moment it was taken: a temperature every 30 minutes, a smart meter every second, a server's CPU load, GPS positions, card transactions, clicks on a page. Lecture 5 calls them time-based logs.

Each record answers three questions: when (the timestamp), what was measured (the values) and about what (which sensor, room or server). Records are added, almost never changed, and read back in blocks of time: "the last hour", "every day in January".

Is it a time series?

A smart meter's readings: yes. New values arrive constantly; you ask about periods.

Is it a time series?

A student's record (name, course, status): no. You look it up by key and update it. That is Week 1 or Week 2 data.

Is it a time series?

Bank transactions: yes, and also more. They are time-stamped events, but also need transactions and constraints. Many systems keep both.

In the lecture notes, purpose-built time-series databases are described as many times faster than MongoDB or an RDBMS for this workload. Benchmark figures like these depend on the workload and on who ran the test, so treat them as an order of magnitude, not a promise.

A2

What a time-series database optimises

Characteristic of the workload (Lecture 5)How InfluxDB is built for it
Time is the main way data is foundEvery point has a timestamp and data is stored in time order, in shards that each cover one block of time.
Very many writes, arriving roughly in time orderWrites are appended to a log and compacted later (the TSM storage engine), rather than inserted into a B-tree in place.
Data is rarely updatedThere is no UPDATE statement. Writing the same series and timestamp again overwrites the values.
Old data is removed in large blocksRetention policies drop whole shards when they expire. DELETE works by time and tag, not by individual values.
Queries read consecutive blocks of timeValues of one field from one series are stored together and compressed, so scanning a range is fast.
Disk I/O, not CPU or RAM, is the bottleneckCompression (often to a few bytes per value) means far less is read from disk.
Think, before Practical 6 T0. Every optimisation in the right-hand column makes something else harder. For each row, ask: what does this make difficult? Updating one record? Enforcing that an e-mail address is unique? Joining a reading to the user who owns the sensor? Your answers are the limitations Practical 6 asks you to explain.

A4

Writing points: line protocol and timestamps

Lecture 5, slide 29: INSERT <measurement>[,<tag-key>=<tag-value>...] <field-key>=<field-value>[,...] [unix-nano-timestamp]. In the influx shell you type INSERT and one point; in a file for influx -import (and from programs) you write the point alone.

The rules that catch people out
  • Exactly one space before the fields and one before the timestamp. Any other space must be escaped: room=lab\ 1.
  • A number is a float unless it ends in i (integer). co2_ppm=612i.
  • String fields need double quotes: note="door open". Tag values never have quotes.
  • The first value written fixes a field's type: co2_ppm=650 after 612i is rejected.
  • No timestamp: the server uses its own clock.
  • Same series + same timestamp = the same point. The second write overwrites its fields. That is the only "update".
Timestamps and precision
  • InfluxDB counts nanoseconds. Most Unix converters give seconds: add nine zeros, or type precision s before inserting.
  • precision rfc3339 makes the shell print readable times (2026-02-02T09:00:00Z). Start every session with influx -precision rfc3339.
  • Times are stored in UTC (the Z). UK time is UTC in winter and UTC+1 (BST) from the last Sunday in March to the last Sunday in October.
  • influx -import -path=file.txt -precision=s loads a file of points; it is run in a terminal, not in the shell.
A5

Schema design: tag or field?

Make it a tag when (slides 18-19)
  • it is metadata you filter on often (which room, which sensor);
  • you will GROUP BY it;
  • it has a limited set of values that does not grow with every reading.
Make it a field when
  • it is the measured value;
  • you will use it in a function: mean(), max(), count(), spread();
  • it must keep a number type (tags are always strings);
  • its values are unique or unbounded (IDs, hashes, e-mail addresses).

Slides 20-21 add: one piece of information per tag; letters and underscores only in names; no InfluxQL keywords as names; and no data in the measurement name. Slides 22-23 show why with blueberries:

A6

Querying with InfluxQL

InfluxQL looks like SQL, with concessions (no joins, ORDER BY time only, GROUP BY tags and time only) and additions for time.

Quotes and case: the silent traps
  • Single quotes for values: WHERE room = 'lab_1'.
  • Double quotes for names (optional unless odd): SELECT "temp_c".
  • WHERE room = "lab_1" compares with a column called lab_1, so returns nothing, with no error.
  • Names and values are case-sensitive. The slide's SELECT * from CPU WHERE “Value” > 0.9 fails on both counts (and its curly quotes).
Time in WHERE
  • time >= '2026-02-02T09:00:00Z' AND time <= '2026-02-02T12:00:00Z'
  • time > now() - 1h (units: ns u ms s m h d w)
  • With GROUP BY time(), always give both ends of the range.
  • tz('Europe/London') at the end shows local time.

A7

Retention, deleting, and choosing a TSDB

Retention policies

Each database has at least one retention policy (RP): how long data is kept. autogen keeps it forever. CREATE RETENTION POLICY thirty_days ON campus DURATION 30d REPLICATION 1 keeps 30 days; data older than that is dropped a shard at a time, and points already older are refused on arrival.

Adding DEFAULT makes every INSERT and SELECT without a named RP use it. Data in autogen then seems to vanish from queries: it is still there as autogen.room_env.

Deleting (slides 31-33)
  • DELETE FROM room_env WHERE room = 'lab_2' AND time < '…': tags and time only, never fields.
  • DELETE WHERE time < '…' without FROM deletes from every measurement.
  • DROP MEASUREMENT energy, DROP SERIES FROM … WHERE tag = '…', DROP DATABASE campus.
  • "Don't update points; delete and reinsert if absolutely necessary."

When to choose a time-series database. High-rate, time-stamped, append-only measurements that you query by period and summarise (IoT, monitoring, metering, finance ticks). Not for data you update by key, need to keep unique, or join: users, accounts, sensor descriptions. Real systems use both, linked by an ID. That is exactly Practical 6, and the kind of choice CW2 asks you to justify (LO2).

SQL to InfluxQL phrasebook

The same questions about the campus readings, asked of a MySQL table room_env(time, room, room_type, temp_c, humidity, co2_ppm, occupancy) and of InfluxDB. Notice which ones InfluxQL makes shorter.

Filter rows
SELECT time, co2_ppm FROM room_env
WHERE room = 'lab_1' AND co2_ppm > 1000
ORDER BY time;
SELECT co2_ppm FROM room_env WHERE room = 'lab_1' AND co2_ppm > 1000
Newest first
SELECT time, temp_c FROM room_env
WHERE room = 'lab_2'
ORDER BY time DESC LIMIT 3;
SELECT temp_c FROM room_env WHERE room = 'lab_2' ORDER BY time DESC LIMIT 3
Average per group
SELECT room, AVG(temp_c) FROM room_env
GROUP BY room ORDER BY room;
SELECT mean(temp_c) FROM room_env GROUP BY room

InfluxDB returns one small table per room; the time column is 1970-01-01 (no time range).

Hourly windows
SELECT DATE_FORMAT(time, '%Y-%m-%d %H:00') AS hour,
       AVG(co2_ppm)
FROM room_env WHERE room = 'lab_1'
GROUP BY hour ORDER BY hour;
SELECT mean(co2_ppm) FROM room_env WHERE room = 'lab_1' AND time >= '2026-02-02T08:00:00Z' AND time <= '2026-02-02T18:00:00Z' GROUP BY time(1h) fill(none)

SQL needs a formatted string to group on; GROUP BY time(1h) is built in, and fill() decides what an empty hour shows.

Highest value, and when
SELECT time, co2_ppm, room FROM room_env
ORDER BY co2_ppm DESC LIMIT 1;
SELECT max(co2_ppm), room FROM room_env

max() is a selector, so the time and room of that reading come with it.

Range (max - min)
SELECT room, MAX(temp_c) - MIN(temp_c) FROM room_env
GROUP BY room ORDER BY room;
SELECT spread(temp_c) FROM room_env GROUP BY room
Change from the previous reading
SELECT time, co2_ppm - LAG(co2_ppm) OVER (ORDER BY time)
FROM room_env WHERE room = 'lab_1'
ORDER BY time;
SELECT difference(co2_ppm) FROM room_env WHERE room = 'lab_1'

SQL also returns the first row, with NULL; InfluxDB starts at the second reading.

Moving average of 3
SELECT time, AVG(temp_c) OVER (ORDER BY time
       ROWS BETWEEN 2 PRECEDING AND CURRENT ROW)
FROM room_env WHERE room = 'lecture_a'
ORDER BY time;
SELECT moving_average(temp_c, 3) FROM room_env WHERE room = 'lecture_a'

SQL also averages the first two rows over fewer readings; InfluxDB waits until three are available.

Running total
SELECT time, SUM(kwh) OVER (ORDER BY time)
FROM energy WHERE room = 'lab_1'
ORDER BY time;
SELECT cumulative_sum(kwh) FROM energy WHERE room = 'lab_1'

Checked: the campus readings were loaded into MySQL 8.0.46 as two tables, and each pair returns the same values from MySQL and from InfluxDB 1.6.7 (9 of 9).

Practical 6: Data modelling in time-series databases

Scenario

A start-up would like to create a scalable data store to manage their IoT data platform. Specifically, they would like this platform to store information regarding API-keys, sensors and users. Storage of user data will encompass an email address (which acts as a user name), a password hash, forename and surname. API-keys will require storage of the key (a string), rights (an integer) and the email address of the associated user. Sensor data will require the sensor ID, sensor label, sensor class, location (string) and raw sensor data to be stored.

Time series databases (TSDBs) are built to store large volumes of variable data arriving at a high rate. The optimisations that make this possible also limit what should be modelled in a TSDB.

    Hint

Identify the information to be stored, the data types involved, logical groupings of data, and which class of database each group goes in.
    Hint

    Which of users, API keys, sensor descriptions and readings are updated by key and need uniqueness? Which arrive continuously with a timestamp? Weeks 1-2 gave you two other classes to choose from.

  3. T2Using your output from T1, develop a detailed storage strategy. Include TSDB modelling (measurements, tags, fields) and the model in your other chosen database (tables or documents). Explain your reasoning.

Downsampling with a continuous query

Keep raw readings for 30 days and hourly means for ever, computed automatically by the server:

CREATE CONTINUOUS QUERY cq_hourly ON campus BEGIN
  SELECT mean(temp_c) AS temp_c, max(co2_ppm) AS co2_max
  INTO autogen.room_env_hourly FROM room_env
  GROUP BY time(1h), room
END
Export a result as CSV

From a terminal, for a spreadsheet or for pandas:

influx -database campus -format csv -precision rfc3339 \
  -execute "SELECT * FROM room_env WHERE room = 'lab_1'" > lab1.csv

from influxdb import InfluxDBClient
c = InfluxDBClient('localhost', 8086, database='campus')

F3

Common misconceptions

Students often say…Correct it to…
"Tags and fields are just two kinds of column."Tags are indexed strings for finding and grouping; fields are typed, unindexed values for computing. The choice decides which queries are possible and fast.
"More tags make queries faster, so tag everything."Every distinct tag combination is a series in memory. Tags with unbounded values make InfluxDB slower, not faster.
"No result means no data."Usually double quotes around a value, the wrong letter case, or a time range in the wrong year.
"I'll UPDATE the reading."There is no UPDATE. Writing the same series and timestamp overwrites; otherwise delete and rewrite.
"A 30-day retention policy keeps the last 30 days of my data."It keeps data whose timestamps are within 30 days of now. Loading last year's data into it drops every point.
"The timestamp converter gave 1509094800, so that's the INSERT time."That is seconds; InfluxDB expects nanoseconds unless you set precision s.
"mean() and max() work the same way."max() is a selector and returns a real point with its real time; mean() is computed, so it has no single time or tag values.

F5

Key terms

Aggregate function
Summarises many points into one value per group or window: mean(), count(), sum(), spread().
Field
A measured value (temperature, count). Has a type; not indexed.
fill()
What an empty GROUP BY time() window shows: null (default), none, previous, linear or a number.
Line protocol
InfluxDB's text format for one point: measurement,tags fields timestamp.
Measurement
The name for a kind of point, like a table name (room_env).
Point
One record: a timestamp with field values, in one series.
Precision
The unit of a timestamp (ns, u, ms, s, m, h), or rfc3339 for readable times in the shell.
Retention policy
How long data is kept (and how many copies); data older than the duration is deleted.
RFC 3339
The readable time format InfluxDB uses: 2026-02-02T09:00:00Z (Z = UTC).
Selector function
Returns one real point from a group: max(), min(), first(), last(), top(), percentile().
Series
All points with the same measurement, tag set and retention policy.
Series cardinality
The number of distinct series. High cardinality uses memory and slows InfluxDB.
Shard
A block of data covering one time range; retention deletes whole shards.
Tag
Indexed metadata (key=value, always a string), used in WHERE and GROUP BY.
Time series
A sequence of measurements, each stamped with the time it was taken.
Transformation function
Computes a new series from a series: moving_average(), derivative(), difference(), cumulative_sum().
Unix time
Time counted from 1970-01-01T00:00:00Z: seconds by most converters, nanoseconds in InfluxDB.
