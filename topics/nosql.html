A1

  • How many tables did your university database need? Were all of them about a "thing", or were some only there to link two things?
  • How did you model one-to-one, one-to-many and many-to-many relationships?
  • How many JOINs did "module, lecturer and student count" (Practical 1, T6) take?

The relational model is very good at consistency and at answering questions nobody planned for. The price is many tables, many JOINs, a fixed schema, and a design built for one server. NoSQL databases trade some of that for other strengths.

A2

What "NoSQL" means

NoSQL is an umbrella term for databases that model data without traditional relational tables. It is a rebellious and inaccurate name:

  • Carlo Strozzi first used it in 1998, for a lightweight database that was in fact relational but did not use SQL.
  • Johan Oskarsson reused it in 2009 to name a meetup on open-source, distributed, non-relational databases. That meaning stuck.
  • Most NoSQL systems now have SQL-like query languages, so it is usually read as "Not only SQL". A more accurate name would be NoREL: not relational.

Non-relational databases existed since the late 1960s, but rose to prominence around 2000, when web-scale companies hit the limits of a single relational server.

A3

Why: the limits of one relational server

Relational limitations at big data scale
  • Volume: very large tables strain one server
  • Variety: a fixed schema copes badly with highly variable data
  • Read performance suffers with variable-length fields
  • Scaling usually means a bigger, more expensive server
NoSQL strengths
  • Scale across many ordinary servers (nodes)
  • Flexible or no fixed schema
  • Data models matched to the access pattern
  • High write and read throughput, often by relaxing consistency

Scaling up (vertical) means a bigger machine: more CPU, RAM and disk. It is simple, but cost rises steeply and there is a ceiling. Scaling out (horizontal) means more machines sharing the data (partitioning, called sharding in MongoDB) and keeping copies (replication). Cheap and almost unlimited, but the copies must be kept in step, and that is where consistency gets hard (A5).

A5

Consistency: ACID and "eventually consistent"

Week 1's relational transactions are ACID. Spread one database across many nodes and keeping every copy identical at every instant becomes slow, or impossible while a node is unreachable. Many NoSQL systems therefore choose eventual consistency: a write is accepted by one node and copied to the others shortly afterwards. Until it arrives, a client reading another node sees the old value (a stale read). The idea is often summarised as BASE: Basically Available, Soft state, Eventually consistent.

Lecture 3's example: X is split across server 1 and server 2; mid-write, server 2 goes down; X is complete on 1 and incomplete on 2. Systems recover from this with logs (journals), as journaling file systems do, rather than per-transaction checks.

Further reading (beyond the lecture): the CAP theorem. When the network between nodes fails (a partition), a distributed database must choose between consistency (refuse requests it cannot answer with the latest data) and availability (answer anyway, possibly stale). Many databases let you choose per operation, as the explorer in C1 does with "read from primary" versus "read from any node".

F2

Common misconceptions

Students often say…Correct it to…
"NoSQL means no SQL at all."Usually "not only SQL": many NoSQL databases have SQL-like languages.
"NoSQL is for unstructured data."Most NoSQL databases hold structured or semi-structured data in a flexible model. Truly unstructured data (video) usually lives in files.
"NoSQL replaces relational databases."Each family fits different data and questions; most real systems use several (polyglot persistence).
"Eventually consistent means sometimes wrong forever."Copies converge once the write has propagated; the window is usually milliseconds to seconds.
"Relational databases cannot scale."They scale up well and can scale out, but with more cost and effort.
F3

Key terms

ACID
Atomicity, Consistency, Isolation, Durability: relational transaction guarantees.
BASE
Basically Available, Soft state, Eventually consistent: the trade-off many NoSQL systems make.
CAP theorem
During a network partition a distributed database must choose consistency or availability (beyond the lecture).
Eventual consistency
Copies may differ briefly after a write but converge once it propagates.
Key-value store
Stores a value under a unique key; the simplest NoSQL model.
NoSQL
"Not only SQL": non-relational databases, usually built to scale out.
Replication
Keeping copies of the same data on several nodes.
Scaling out / up
Adding more machines / a bigger machine.
Sharding
Splitting a collection across nodes by a key (partitioning).
Stale read
Reading an old value from a copy that has not received the latest write.
Wide-column store
Rows with flexible column families, built for very large write volumes (Cassandra, HBase).
