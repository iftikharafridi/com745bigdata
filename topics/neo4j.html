A

Understand

From rows and documents to nodes and relationships.

A1

Why a graph database?

A graph database is a NoSQL database that stores data as a connected graph (Lecture 6, slides 3-4). Relational databases store connections indirectly, as matching values in foreign-key columns, and work them out at query time with joins. A graph database stores each connection as a thing in its own right, so following it is a direct step.

That makes questions about connections natural and fast: friends of friends, "people who bought this also bought", how two things are linked, chains of any length. Lecture 6's examples are recommendation engines (Facebook's social graph, slides 15-21) and NASA's lessons-learned knowledge graph, where engineers found an Apollo-era answer for Orion "in hours instead of months" (slides 22-25).

Graph-shaped question

"Which students share a module with Priya, and what else do they take?" Several hops, each following stored links.

Graph-shaped question

"Are these two bank accounts connected through shared phones or addresses, within four steps?" The depth is unknown in advance.

Not graph-shaped

"Average mark per module this year." One pass over a table: SQL, or a column store at scale, does this better.

A2

The property graph model

PartWhat it isLecture 6 example (slides 6-11)
NodeAn entity. Has zero or more labels saying what kind of thing it is.(:Person {name: 'John', age: 27})
RelationshipA connection between two nodes. Always has exactly one type and one direction (though you can query it either way).(john)-[:FRIEND_OF]->(sally)
PropertyA key-value pair on a node or a relationship: strings, numbers, booleans or lists of them.since: '2013-09-01' on FRIEND_OF; rating: 5 on HAS_READ

Rules of thumb
  • Nouns become nodes with a label (Student, Module); verbs become relationship types (TEACHES, REGISTERED_ON).
  • A link table becomes a relationship; its extra columns become relationship properties.
  • Something you search or group by, and that many nodes share, may deserve its own node (a Course, a City) rather than a repeated property.
  • A role belongs on the relationship: an actor is a Person who ACTED_IN a Movie, not a different kind of node (Practical 9 T1).
  • Conventions: labels in CamelCase, relationship types in UPPER_SNAKE_CASE, properties in camelCase.
A4

Querying with Cypher patterns

Cypher describes what to find by drawing it in ASCII art: round brackets for nodes, square brackets for relationships, an arrow for direction (slides 32-52).

MATCH (s:Student {name: 'Priya Patel'})-[r:REGISTERED_ON]->(m:Module)
WHERE r.semester = 'Semester 1'
RETURN s.name, m.code, r.date
Reading the pattern
  • s, r, m are variables: names for what matched, used in WHERE and RETURN.
  • :Student is a label, :REGISTERED_ON a type. Both are case-sensitive.
  • -> follows the stored direction; - with no arrow matches either way.
  • (m) with no label matches any node; () any node you do not need to name.
Three habits that save hours
  • A wrong label, type or direction is not an error: you get no rows and a warning.
  • Variables last for one statement. MATCH existing nodes before you CREATE relationships to them.
  • Within one MATCH a relationship is used at most once. A pattern that needs to walk the same relationship twice finds nothing; split it with WITH.

A6

Paths, depth and why hops are cheap

-[*1..3]- follows one to three relationships; shortestPath((a)-[*]-(b)) finds the fewest hops between two nodes. In SQL these need recursive queries, or one join per hop, written in advance.

Neo4j stores, in each node, direct references to its relationships (index-free adjacency). Following a relationship therefore costs about the same however large the database is; a join instead looks each value up in an index whose cost grows with the table. Slide 21's figures (RDBMS, 1,000 people: 2,000 ms; graph, 1,000 or 1,000,000 people: 2 ms) come from a vendor benchmark: read them as a shape, not as a promise.

A7

When to choose a graph, and the query languages

Choose a graph when
  • the questions are about connections, paths or neighbourhoods;
  • the depth is variable or unknown (fraud rings, supply chains, networks);
  • the schema changes often and relationships carry their own data;
  • you need recommendations or a knowledge graph.
Choose something else when
  • you aggregate whole tables (reporting, analytics): relational or columnar;
  • data arrives as a high-rate stream of measurements: time series (Week 3);
  • you store self-contained records read whole: documents (Week 2);
  • you need to scale writes across many servers: graphs are hard to partition.

SQL to Cypher phrasebook

The same questions about the university, asked of MySQL (Week 1) and of the graph. Joins become patterns; link tables become relationships.

Filter and sort
SELECT Forename, Surname FROM Student
WHERE CourseCode = 'MSCDS'
ORDER BY StudentID;
MATCH (s:Student)-[:ENROLLED_ON]->(:Course {code: 'MSCDS'})
RETURN s.name
ORDER BY s.id;

The course is a node, not a column: the filter becomes part of the pattern.

Count missing values
SELECT COUNT(*) FROM Student WHERE Mobile IS NULL;
MATCH (s:Student) WHERE s.mobile IS NULL
RETURN count(*);
JOIN through a link table
SELECT s.StudentID FROM Student s
JOIN Registration r ON r.StudentID = s.StudentID
WHERE r.ModuleCode = 'COM748'
ORDER BY s.StudentID;
MATCH (s:Student)-[:REGISTERED_ON]->(:Module {code: 'COM748'})
RETURN s.id ORDER BY s.id;

The Registration table is the REGISTERED_ON relationship.

Two joins
SELECT m.ModuleCode, l.Forename, l.Surname
FROM Module m JOIN Lecturer l ON l.LecturerID = m.LecturerID
ORDER BY m.ModuleCode;
MATCH (l:Lecturer)-[:TEACHES]->(m:Module)
RETURN m.code, l.name ORDER BY m.code;
GROUP BY
SELECT CourseCode, COUNT(*) FROM Student
GROUP BY CourseCode ORDER BY CourseCode;
MATCH (s:Student)-[:ENROLLED_ON]->(c:Course)
RETURN c.code, count(s) ORDER BY c.code;

No GROUP BY: every column that is not an aggregate is a grouping key.

LEFT JOIN and COUNT(column)
SELECT m.ModuleCode, COUNT(r.StudentID) AS students
FROM Module m LEFT JOIN Registration r ON r.ModuleCode = m.ModuleCode
GROUP BY m.ModuleCode ORDER BY m.ModuleCode;
MATCH (m:Module)
OPTIONAL MATCH (s:Student)-[:REGISTERED_ON]->(m)
RETURN m.code, count(s) AS students ORDER BY m.code;
NOT EXISTS
SELECT s.StudentID, s.Forename FROM Student s
WHERE NOT EXISTS (SELECT 1 FROM Registration r
                  WHERE r.StudentID = s.StudentID);
MATCH (s:Student)
WHERE NOT (s)-[:REGISTERED_ON]->()
RETURN s.id, s.name;
HAVING
SELECT ModuleCode, COUNT(*) AS n FROM Registration
GROUP BY ModuleCode HAVING COUNT(*) >= 6
ORDER BY ModuleCode;
MATCH (:Student)-[:REGISTERED_ON]->(m:Module)
WITH m, count(*) AS n WHERE n >= 6
RETURN m.code, n ORDER BY m.code;
Self-join: classmates
SELECT DISTINCT o.StudentID
FROM Registration me
JOIN Registration o ON o.ModuleCode = me.ModuleCode
                   AND o.StudentID <> me.StudentID
WHERE me.StudentID = 1004
ORDER BY o.StudentID;
MATCH (:Student {id: 1004})-[:REGISTERED_ON]->(:Module)
      <-[:REGISTERED_ON]-(o:Student)
RETURN DISTINCT o.id ORDER BY o.id;

A self-join in SQL; in Cypher, out to the module and back in.

Checked: each pair returns the same values from MySQL 8.0.46 and from the Cypher emulator (9 of 9); FalkorDB, a separate graph database, agrees on 8 of 9 (the others differ only because FalkorDB lets one pattern reuse a relationship, which Neo4j does not).

Practical 9: Modelling data within graph databases

Scenario

A large online retailer which specialises in retailing films would like to model information about films. Specifically, the retailer would like to store information about films, actors, producers, writers and publishers. Information about people in the database should cover their full name, as a single field, and the year they were born. Films should be stored along with their title, the year they were released and the tagline.

Graph databases are best suited to modelling and querying the interrelationships between entities. They are optimised for this in their data structure and query language, but these optimisations bring limitations that may limit their usefulness.

  1. T0Identify some limitations introduced by graph databases. How are these introduced by optimisations?
    Hint

    Think about what index-free adjacency (each node pointing straight to its relationships) makes cheap, and what it makes expensive: scanning every node to sum a property, splitting a graph across many servers, very high-rate writes, enforcing a schema.

  2. T1Using pen and paper (recommended) or software, conceptualise how a graph covering the scenario would be modelled. Incorporate all potential links: for example, a person may act in, write and direct a movie.
    Hint

    Draw circles for node labels and arrows for relationship types. Is "actor" a kind of node, or a relationship a Person has with a Movie? Where does "the role played" belong? Is a publisher a Person?

  3. T2What other roles could graph databases have in a larger big data platform? For example, a probabilistic text-mining platform that identifies interactions between people, or a platform that processes mass financial transactions to identify fraud.
    Hint

    Slides 15-25 (recommendations, knowledge graphs). For fraud: shared phone numbers, devices or addresses linking accounts into rings. For text mining: people as nodes, co-mentions as weighted relationships.

  4. T3Extending from T2, identify some database types which would complement a graph database to optimally store data in both scenarios.
    Hint

    Where would the raw documents live? The stream of transactions over time? The customer master records? You have met document, time-series and relational databases in Weeks 1-3; Hadoop comes in Week 6.

F3

Common misconceptions

Students often say…Correct it to…
"Relational databases are about relationships.""Relational" refers to relations, the mathematical name for tables. Connections between rows are computed with joins; a graph database stores them.
"No rows means the data is not there."Usually a typo in a label or type, the wrong case, or an arrow pointing the wrong way. Read the warning.
"CREATE (a)-[:R]->(b) links my existing a and b."Only if a and b were bound by a MATCH in the same statement; otherwise it creates two new, empty nodes.
"An actor is a kind of node."Acting is a relationship between a Person and a Movie; the same person can also direct.
"Graphs are faster at everything."They are faster at following connections. Whole-table aggregation, high-rate writes and scaling out are weaker.
"MERGE never creates duplicates."MERGE matches the whole pattern you write. A different property value in the pattern means "not found", so it creates another node.
"A schema-free graph needs no design."Labels, types, directions and what becomes a node decide which questions are easy. Constraints add the rules the database will not assume.

F5

Key terms

Cypher
Neo4j's declarative graph query language, now also used by other graph databases (openCypher).
DETACH DELETE
Delete nodes together with all their relationships.
GQL
ISO/IEC 39075:2024, the international standard graph query language, closely based on Cypher.
Index-free adjacency
Each node stores direct references to its relationships, so following one costs the same however big the graph is.
Label
A tag that groups nodes by kind (Student, Module). A node can have several.
MERGE
Match a whole pattern, or create it if it does not exist.
Node
An entity in the graph: a person, a module, a film.
OPTIONAL MATCH
Like MATCH, but keeps the row with nulls when the pattern is not found (the LEFT JOIN of Cypher).
Path
A sequence of nodes joined by relationships; length = number of relationships.
Pattern
ASCII-art description of nodes and relationships to find: (a:Student)-[:REGISTERED_ON]->(m:Module).
Property
A key-value pair on a node or a relationship.
Property graph
The data model of Neo4j: nodes and relationships, both with properties; nodes have labels, relationships have a type and direction.
Relationship
A named, directed connection between two nodes (an edge). Always has exactly one type.
Relationship uniqueness
Within one MATCH, a relationship is used at most once, so patterns do not walk back along the edge they came in on.
Uniqueness constraint
A rule that no two nodes with a label share a property value; also creates an index.
Variable-length pattern
-[*1..3]-: follow between one and three relationships.
