A

Understand

The ideas, in the order you need them: from data to a tested design.

A1

Data, and when it becomes Big Data

Data is recorded facts, observations or values. On its own it has little meaning; organised and put in context it becomes information. The same student can be stored in very different shapes:

FormExampleUsually lives in
Structured1001 | Ahmed | Ali | MSCCST | 72A table with fixed columns (relational database)
Semi-structured{"id": 1001, "name": "Ahmed Ali", "modules": ["COM745", "COM746"]}JSON or XML documents (document database)
UnstructuredAn email asking for an extension; a photo of his ID cardFiles or object storage, with metadata in a database

Notice the JSON record holds a list of modules inside one record. A relational table cannot do that in one cell; this comes back as First Normal Form in A9.

Big Data is data whose volume (how much), velocity (how fast it arrives) or variety (how many shapes) makes it hard to store and process with traditional single-server tools. Two more Vs are often added: veracity (how trustworthy) and value (what it is worth). One V is enough to cause the problem: a small but very fast stream of sensor readings is "big" without being huge.

A2

Which database for which data?

No database is best for everything. Each family is optimised for one shape of data and one pattern of use. This module visits four of them in turn.

Data and needFamilyIn this module
Structured, related data that must stay consistentRelationalMySQL, Week 1
Flexible or semi-structured documentsDocument (NoSQL)MongoDB, Week 2
Time-stamped sensor or monitoring dataTime-seriesInfluxDB, Week 3
Highly connected data (who knows whom)Graph (NoSQL)Neo4j, Week 4

Avoid saying "NoSQL is for unstructured data". Many NoSQL systems suit flexible or semi-structured data; truly unstructured data (video, images) is usually stored as files, with its metadata in a database.

A3

Database, DBMS and RDBMS

A database is an organised collection of related data that can be stored, retrieved and managed efficiently. Databases are older than computers: a phone book is one. Its records are entries, its fields are name, address and number, and its alphabetical order is an index. That index makes one question fast (find Khan) and others slow: finding everyone in Birmingham means reading every page. Two people called John Brown show that a name is not a key.

A university before databases kept separate filing cabinets for students, modules, lecturers and registrations, with the same student's address copied into several. That causes six problems a database management system is built to solve:

ProblemAt the universityDBMS answer
RedundancyAhmed's address is in five filesStore each fact once (normalisation)
InconsistencyRegistry says "Ahmed Ali", Assessments says "A. Ali"Keys and constraints
Difficult retrieval"Which COM745 students does Dr Brown teach?" means pulling three cabinetsA query language (SQL)
SecurityHard to let lecturers see marks but not home addressesAccess control, views
Concurrent accessTwo staff need the same paper file at onceConcurrency control, transactions
Backup and recoveryOne spilled coffee and the record is goneLogging, backup, durability
  • Database: the organised data itself (the library's books).
  • DBMS: the software that creates, manages, queries and protects it (the librarian and catalogue).
  • RDBMS: a DBMS based on the relational model: tables, keys and SQL. MySQL, PostgreSQL, SQL Server and Oracle are RDBMSs; MongoDB is a DBMS but not relational.
A4

The relational model, and NULL

A relational database stores data in tables (relations) linked by keys, instead of repeating everything in one place. Textbooks and exam papers use two vocabularies; learn both.

Everyday / SQL termFormal termIn the Student table
TableRelationStudent
Row, recordTuple1002, Sarah, Khan, …
Column, fieldAttributeEmail
Number of rowsCardinality24
Number of columnsDegree10
Allowed values for a columnDomainEmail: text up to 100 characters

Row order has no meaning, and no two rows may be identical.

NULL means a value is missing, unknown or not applicable. It is not zero and not an empty string. Three consequences:

  • NULL is not equal to anything, not even another NULL. WHERE Mobile = NULL finds nothing; write WHERE Mobile IS NULL.
  • NULL is where partial participation shows up ("a lecturer may teach no module"). Total participation becomes NOT NULL.
  • A primary key can never be NULL (entity integrity). Whether DateOfBirth or Email may be NULL is a business rule: ask the client.

A6

Constraints protect the data

Entity integrity: a primary key value is unique and never NULL. Referential integrity: every foreign key value matches an existing primary key (or is NULL, if allowed); you cannot register student 9999 if there is no student 9999. A good design does not only store correct data: it stops incorrect data getting in.

ConstraintRuleWithout it…MySQL error
PRIMARY KEYUnique and not NULLTwo rows could both be student 10011062

NOT NULLA value must be suppliedA module with no lecturer1048

A7

Design first: the lifecycle and ER modelling

"A university asks us for a database. What do we do first?" Not open MySQL. A wrong design is expensive to fix once data is loaded, so developers follow a lifecycle, and testing often sends them back to the start.

Requirements become short, testable business rules (Practical 0 scenario): each course has a unique code, name and level 4-8, and one coordinating lecturer; courses consist of modules and a module can be in several courses; each module is delivered by one lecturer, and a lecturer may deliver several or none; a student is on one course and registers for many modules, and we record the date and semester of each registration.

Read the rules for nouns (entities), facts about nouns (attributes), verbs (relationships), quantity words like "one", "many", "each" (cardinality), and "must", "may", "or none" (participation). RegistrationDate belongs to no entity: it describes the act of registering, so it is an attribute of the relationship.

Read every relationship in both directions and say both sentences: "One lecturer delivers many modules. Each module is delivered by one lecturer." If both directions say "many", it is M:N. Cardinality answers how many?; participation answers is it compulsory? Keep them as two questions.

A weak entity cannot be identified by its own attributes. A dependent called Sara is not unique across a company; "employee 7's dependent Sara" is. University version: "assessment 1 of COM745". Try the weak-entity scenario in the builder below.

A8

From ER diagram to tables

Mapping turns the picture into tables with a small set of mechanical rules. Two rules carry most of the weight: a 1:N relationship puts the foreign key on the N side (a module row has room for exactly one LecturerID; a list of modules on the lecturer side would break 1NF), and an M:N relationship becomes a new table whose primary key is both foreign keys. For 1:1, put the FK on the side with total participation and add UNIQUE.

Lecturer     (LecturerID PK, Forename, MiddleName, Surname, DateOfBirth, Email UNIQUE, RankLevel)
Course       (CourseCode PK, CourseName, AccreditationLevel, CoordinatorID FK → Lecturer)
Module       (ModuleCode PK, ModuleName, Credits, LecturerID FK → Lecturer)
CourseModule (CourseCode PK/FK → Course, ModuleCode PK/FK → Module)
Student      (StudentID PK, Forename, MiddleName, Surname, DateOfBirth, Email UNIQUE,
              Mobile, EnrolmentLevel, CourseCode FK → Course, Status DEFAULT 'Active')
Registration (StudentID PK/FK → Student, ModuleCode PK/FK → Module, RegistrationDate, Semester)

The full university schema, mapped from the ER diagram above. This is the shared dataset used in every demo, explorer and the playground. The Lectures 1-2 notes call the lecturer entity Tutor; the practicals and this site say Lecturer.

A9

Normalisation: each fact in one place

Normalisation checks that every fact is stored exactly once, so the database cannot contradict itself. The tool behind it is the functional dependency: A → B means that knowing A tells you exactly one B (StudentID → StudentName). Test: "if I know the left side, is there only one possible right side?" StudentName → StudentID fails, because two students can share a name.

In a registrations spreadsheet keyed by (StudentID, ModuleCode): StudentName depends on part of the key (a partial dependency); LecturerName depends on LecturerID, which depends on ModuleCode (a transitive dependency). Only RegistrationDate needs the whole key.

  • 1NF: one atomic value per cell, every row identifiable.
  • 2NF: 1NF, and no partial dependencies. A table with a single-column key is automatically in 2NF.
  • 3NF: 2NF, and no transitive dependencies. Every non-key attribute depends on the key, the whole key, and nothing but the key (Kent).

Two routes, one answer: the 3NF tables match what the ER mapping produced. A well-drawn ER diagram usually lands in 3NF already; normalisation is the check, and the tool for fixing spreadsheets and legacy tables that were never designed.

Is a phone number an INT? No. 02081234567 loses its leading zero, +44 and spaces cannot be stored, and nobody adds two phone numbers. If you would never do arithmetic on it, it is probably not a number: phone numbers, postcodes and module codes like COM745 are VARCHAR.

A11

Indexes and transactions

An index is the phone book's alphabetical order rebuilt inside the database: CREATE INDEX idx_student_surname ON Student (Surname); lets MySQL jump to "Khan" instead of reading every row. MySQL indexes every primary key and UNIQUE column automatically, and InnoDB indexes each foreign key. Indexes speed up reads but cost storage and slow every write, so index the columns people search and join on.

A transaction groups statements into one unit that happens completely or not at all. A bank transfer is two UPDATEs; enrolling a student is a Student row plus Registration rows. Relational databases guarantee ACID:

Atomicity

All or nothing. A half-finished transfer is rolled back.

Consistency

Each transaction moves the database from one valid state to another; constraints still hold.

Isolation

Concurrent transactions don't see each other's half-done work.

Durability

Once committed, a change survives a crash or power cut.

Many NoSQL systems relax some of these guarantees in exchange for scale and speed. That trade-off returns in Week 2 and again with Hadoop.

More examples for home study

Inline constraints

The same Module table with constraints written inside CREATE TABLE, the style used in many textbooks:

CREATE TABLE Module (
  ModuleCode VARCHAR(10)  PRIMARY KEY,
  ModuleName VARCHAR(100) NOT NULL,
  Credits    TINYINT      NOT NULL CHECK (Credits > 0),
  LecturerID INT          NOT NULL,
  FOREIGN KEY (LecturerID) REFERENCES Lecturer (LecturerID)
);
ON DELETE CASCADE

Delete a student and their registrations go too. Convenient, but think first: is losing the history acceptable?

ALTER TABLE Registration
  DROP FOREIGN KEY fk_registration_student;
ALTER TABLE Registration
  ADD CONSTRAINT fk_registration_student
  FOREIGN KEY (StudentID) REFERENCES Student (StudentID)
  ON DELETE CASCADE;

F3

Common misconceptions

Students often say…Correct it to…
"A database and a DBMS are the same thing."The database is the data; the DBMS is the software managing it.
"NULL means zero or an empty string."NULL means missing, unknown or not applicable, and is tested with IS NULL.
"Every relationship becomes a table."Only M:N relationships (and multivalued attributes) need a new table; 1:N becomes a foreign key.
"The foreign key goes on the 1 side."It goes on the N side, which has one value per row.
"A composite key is two primary keys."It is one primary key made of two columns.
"Cardinality and participation are the same."Cardinality is how many; participation is whether it is compulsory.
"Normalisation means splitting tables as much as possible."Split only to remove a named dependency; over-splitting adds needless JOINs.
"A phone number should be an INT."It is an identifier: leading zeros and +44 matter. Use VARCHAR.
"More indexes always make it faster."Indexes speed reads but slow every write and cost storage.
"If it inserted without an error, the design is right."Test by inserting bad data: a good design rejects it.

F5

Key terms

ACID
Atomicity, Consistency, Isolation, Durability: the guarantees a relational transaction gives.
Alternate key
A candidate key not chosen as the primary key; enforced with UNIQUE.
Anomaly
An update, insertion or deletion problem caused by storing a fact more than once.
Attribute
A column; a fact describing an entity.
Candidate key
A minimal set of columns that uniquely identifies a row.
Cardinality (ER)
How many: 1:1, 1:N or M:N. (In the relational model, cardinality also means the number of rows.)
Composite key
A key made of two or more columns together.
Constraint
A rule the DBMS enforces: PRIMARY KEY, FOREIGN KEY, NOT NULL, UNIQUE, CHECK, DEFAULT.
DBMS
Database management system: the software that creates, manages, queries and protects a database.
DDL / DML
Data Definition Language changes structure (CREATE, ALTER, DROP); Data Manipulation Language changes rows (INSERT, UPDATE, DELETE).
Degree
The number of columns in a relation.
Derived attribute
A value calculated from others (Age from DateOfBirth); usually not stored.
Entity
A thing the organisation stores data about: Student, Module.
Foreign key
A column whose values must match a primary key in another (or the same) table.
Functional dependency
A → B: knowing A determines exactly one value of B.
Index
A structure that lets the DBMS find rows without reading the whole table.
JOIN
Combines rows from two tables where a condition (usually PK = FK) matches.
Multivalued attribute
An attribute that can hold several values (phone numbers); mapped to its own table.
Normal forms
1NF: atomic values. 2NF: no partial dependency. 3NF: no transitive dependency.
NULL
Missing, unknown or not applicable. Not zero, not empty text. Tested with IS NULL.
Participation
Whether taking part in a relationship is compulsory (total, double line) or optional (partial).
Primary key
The candidate key chosen to identify rows; unique and never NULL.
RDBMS
A DBMS based on the relational model: tables, keys and SQL.
Referential integrity
Every foreign key value refers to a row that exists.
Relation / tuple
Formal names for a table and a row.
Super key
Any set of columns that uniquely identifies a row (not necessarily minimal).
Transaction
A group of statements that succeed or fail as one unit.
Weak entity
An entity identified only together with its owner (dependent of an employee).
